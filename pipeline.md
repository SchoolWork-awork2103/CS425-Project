# Overview

**Output format:** every poem is a **quatrain with an AABB rhyme scheme**: four lines, where lines 1 and 2 rhyme with each other and lines 3 and 4 rhyme with each other, using a different rhyme sound.

**Pipeline at run time** (no API calls anywhere):
user message → NLU → dialogue manager → rhyme planner → retrieval → generator (several candidates) → reranker → reply

**Where an LLM is used** (offline, before training only): generating the modern AABB quatrain corpus for pretraining, the diss data, the NLU training data, intensity labels and two kinds of reranker negatives (flat and non-rhyming), and optionally as a second judge in evaluation. All of it uses Qwen3-32B-FP8 with thinking off.

**Priority tags**
- **[Core]**: needed for a working, valid project
- **[Recommended]**: makes it properly conversational and lifts quality
- **[Optional]**: extras if time allows

**Systems to compare**

| ID | Generator | Course link | Priority |
|---|---|---|---|
| A | GRU language model, traits as prefix | Week 4 | Core |
| B | GRU encoder-decoder with attention | Week 5 | Optional |
| C | Small Transformer from scratch | Week 6 | Optional |
| D | Qwen2.5-1.5B-Instruct + LoRA, run locally | Week 10 | Recommended |

# Phase 0: Setup [Core]

1. **Repo:** one GitHub repo with folders
   `data/ phonetics/ generation/ retrieval/ reranker/ nlu/ dialogue/ eval/ app/`
   plus a shared `requirements.txt`, fixed random seeds, and a `config.yaml` for paths and hyperparameters.
2. **Compute:** Colab T4 for training; the LLM data (1a, 1b, 1d, 1e) is generated with vLLM on the cluster's 48 GB GPU (L40); checkpoints in a shared Drive folder with agreed names (e.g., `gen_A_stage2_best.pt`).
   - Each generation notebook loads its own copy of the model (about 40 GiB at `gpu_memory_utilization=0.90`), so run them one at a time and shut down the previous kernel first. `negatives_gen.ipynb` checks for free GPU memory before loading.
   - Every notebook has a `MODE` switch: run `"pilot"` and read the output, then `"full"` with Restart & Run All. Raw output goes to `llm_out/` (`llm_pilot_out/` for pilots) and is copied to that dataset's `llm_out/` in the repo (e.g. `data/nlu/llm_out/`). 3. **Trait list:** 40 positive traits, each with a "flip" angle and synonyms, in `data/traits.json`:
   ```json

   ```
   Hold out **5 traits** that never appear in training. They're used only to test generalization.
4. **Frozen evaluation prompts:** write 50 test inputs now, before any model exists:
   - 20 single-trait, 20 with two or three traits, 5 with held-out traits, 5 with no or unclear traits
   - commit as `eval/prompts.json` and never change it

# Phase 1: Data

### 1a. Modern AABB quatrain corpus (LLM-generated) [Core]
This replaces the Gutenberg Poetry Corpus. That corpus is mostly old verse in archaic language, far from the modern, conversational style of the disses, and only a small share of its 4-line chunks are AABB. Instead, every pretraining example is now a modern AABB quatrain, generated by `quatrain_gen.ipynb`.

1. **Generation.** The generator is **Qwen3-32B-FP8** (thinking mode off), run locally with vLLM. In a 300-prompt pilot it beat Qwen3-30B-A3B and Qwen2.5-32B-AWQ on yield: 56% of prompts gave a kept quatrain, and kept quatrains averaged 4.4/5 from the judge.
   - Each prompt combines one of about 600 everyday topics (`topics.json`), one of 14 tones and one of 3 voices (I / you / narrator), with two worked examples given as earlier chat turns.
   - The model first writes a `RHYMES:` plan, then each line prefixed with its end word, e.g. `[red] My battery icon has just turned red,`. The parser strips both the plan and the prefixes.
   - It samples 4 candidates per prompt.
2. **Form checks** on each candidate:
   - exactly 4 lines
   - lines 1–2 and lines 3–4 rhyme (CMUdict), and the A and B rhymes use different sounds
   - no identical rhymes (play/replay, one/won)
   - 6–12 syllables per line, with the two lines of each couplet within 3 syllables of each other
   - at most 15% of words missing from CMUdict
   - no rare or made-up end words (wordfreq Zipf ≥ 2.5)
3. **Quality judge.** The same model rates each candidate that passes the form checks from 1 to 5 for sense and naturalness, using a rubric with four calibration examples. Candidates scoring 4 or 5 are kept. From each prompt, the highest-scoring candidate is saved; ties go to the candidate whose rhyme pairs are least used so far.
4. **Dataset filters:**
   - exact duplicates
   - near-duplicates (ROUGE-L above 0.7 against saved quatrains that share a rhyme pair)
   - quatrains that reuse two or more lines from earlier ones
   - any rhyme pair already used 50 times, which spreads out the rhyme vocabulary
   - copies of the worked examples
5. **Size and format.** The target is **20,000 quatrains** (raise it to 50,000 if Stage 1 needs more). They are saved in `gen_out/qwen3-32b/quatrains.jsonl`, one per line:
   ```json
   {"id": 2, "topic": "replacing old batteries", "tone": "tender", "voice": "first person (I)",
    "lines": ["I tucked your old batteries far away,", "they're ghosts from a time we used to play.",
              "I hold them now in my careful hands,", "while your new ones hum inside their stands."],
    "rhymes": [["away", "play"], ["hands", "stands"]], "syllables": [10, 9, 9, 9],
    "score": 4, "model": "Qwen/Qwen3-32B-FP8", "chunk": 0}
   ```
6. **Prepare for training.** Lowercase and normalize punctuation the same way as the diss data.
   - Every quatrain is already AABB, so the old "tag the AABB chunks and oversample them" step is no longer needed.
   - The `rhymes` field gives the Stage 1 `<rhymes>` conditioning words directly.
7. **Spot-check:** skipped. The judge is the model rating its own output, so the report should mention that kept quatrains were not checked by hand.
8. **Split** 95/5 into train and validation **by topic group**, so the validation subjects are unseen. Topics are linked when they share a noun (after stemming, or one noun starting or ending with the other, such as toast/toaster), and whole groups go to validation, so no validation topic shares a noun with a training topic.
9. **Record** the model, prompts, filter settings, judge rubric and date for the report. The run settings and statistics are saved in `gen_out/qwen3-32b/meta.json`, and the per-chunk rejection reasons in `progress.jsonl`.

### 1b. Diss dataset with an LLM [Core]
Generated by `data/disses/diss_gen.ipynb`, then cleaned and split by `data/disses/prepare_disses.py`.

1. **Style.** The style comes from `diss_style_examples.csv`, the team's hand-picked roasts. Each is a two-line jab: line 1 throws the brag back ("You claim you're…"), line 2 flips it into the insult. A diss is **two such jabs**, which makes an AABB quatrain.
2. **Prompt.** One diss per request, with the trait(s) and their flip side, the intensity (mild or harsh), three worked examples as earlier chat turns (built from CSV jabs, leaving out examples close to the requested trait so the model writes new jokes) and the rules: no swear words or vulgar language, nothing hateful about race, religion, gender, sexuality or disability. The model writes a `RHYMES:` plan, then each line prefixed with its end word in brackets, as in 1a. It samples 4 candidates per request, and at most one is kept.
3. **Targets**, 5,200 disses wanted:
   - 35 training traits × 15 single-trait disses
   - 250 trait pairs × 6
   - 100 trait triples × 4
   - 5 held-out traits × 15 (test set only)
   - 100 generic fallback disses with an empty trait field
   - each of these for both mild and harsh
4. **Form checks** (`data/form_checks.py`, the 1a rules with the line length of the CSV): 4 lines, AABB with different A and B sounds, **6–18 syllables per line with couplets within 5** (`diss_form` in `config.yaml`), no rare end words, leftover tags or stapled end words.
5. **Judge.** The same model lists any line that doesn't make plain sense, then scores how hard the roast hits from 1 to 5. An unclear line caps the score at 2. Scores of 4 and 5 are kept.
6. **Dataset filters:** near-duplicates (ROUGE-L above 0.7), any rhyme pair already used 15 times, near-copies of the CSV jabs, then in `prepare_disses.py` toxicity (Detoxify limits in `config.yaml`, plus `blocklist.txt`), digits and symbols, and non-Latin text.
7. **Result.** 33,000 requests (14% gave a kept diss), so 4,492 of the 5,200 were kept and 393 trait combinations ended short. After the `prepare_disses.py` filters, 4,374 remain (191 of them fallback).
8. **Manual review:** skipped. Every diss that passes the filters is kept (`python data/disses/prepare_disses.py auto`); the generation judge stands in for it, which the report should say. So `corpus/dropped.jsonl` is empty, and 1e gets no review-dropped negatives.
9. **Splits:** 80/10/10 over the training traits: 3,382 train, 423 val, 569 test. All 146 held-out-trait disses go to test only.
10. **Record** the LLM used, the prompts and the date for the report (`llm_out/disses_meta.json`), and check the provider's terms on using outputs for training.

### 1d. NLU data [Recommended]
1. **Intents:** `request_diss`, `another_one`, `make_meaner`, `make_softer`, `greet`, `goodbye`, `out_of_scope`
2. **Slot:** `TRAIT` in BIO format
3. **Generation** (`data/nlu/nlu_gen.ipynb`), 228 requests of 20 messages each (5 for pairs), each request in one of six styles: casual texting with typos, polite, very short, Gen Z slang, rambling, non-native English.
   - Trait messages: 2 requests per trait (training and held-out), mixing direct mentions with indirect ones ("people say I never shut up about history"), plus 60 random training-trait pairs. Each comes with the exact words that express each trait (the span). The prompt names the exact trait keys; a span labelled with a synonym ("clever") is mapped back to its trait ("smart"), and curly quotes are straightened in spans as in the text.
   - Other intents: `request_diss` with no trait (8 requests), `another_one`, `make_meaner`, `make_softer` and `out_of_scope` (15 each), `greet` and `goodbye` (10 each).
   - Messages about held-out traits are marked `heldout`.
4. **Result:** 3,579 messages (4 requests gave unreadable JSON). Raw output: `data/nlu/llm_out/` (`nlu.jsonl`, `nlu_meta.json`, and the executed notebook).
5. **Prepare** (`python data/nlu/prepare_nlu.py`, into `data/nlu/corpus/`): drops duplicates, messages that appear under two intents, trait messages with no span, and spans not found in the text, which keeps 3,481. Spans become BIO tags over whitespace tokens.
6. **Split** 80/10/10 within each intent; held-out-trait messages (197) go to test only. `spot_check.csv` samples 10% for a hand check (mark `ok` y/n). Expect some loose spans and a few messages under the wrong intent.

### 1e. Reranker negatives [Recommended]
Negatives for the trait-fit classifier (Phase 5), about 64 per training trait. **Apart from its own flaw, every negative passes the disses' form check** (`diss_form`), so the classifier can't tell it from a real diss by rhyme, line length or voice. Built by `python data/negatives/prepare_negatives.py` into `data/negatives/corpus/`, from the raw LLM output in `data/negatives/llm_out/`.

| Type | Source | Kept |
|---|---|---|
| `flat` | LLM (`data/negatives/negatives_gen.ipynb`): rhyming quatrains to "you" about the trait, with no joke and no flip side; one worked example in the prompt | 382 |
| `non_rhyming` | LLM: roasts to "you" about the trait whose lines don't rhyme; must pass the length checks and not rhyme | 453 |
| `off_topic` | quatrain corpus (1a, train split only): fine AABB quatrains that aren't roasts, from the longer half, each used once | 700 |
| `wrong_trait` | training disses (1b) labelled with a trait they weren't written for, never one in the same `CLOSE` group (e.g. calm / easygoing / patient) | 700 |
| `review_dropped` | disses dropped in manual review | 0 (review skipped) |

- **LLM run:** 4 `flat` and 2 `non_rhyming` requests of 10 per training trait (210 requests, 9 gave unreadable JSON): 2,002 quatrains, 835 kept. `flat` passes the rhyme check about 30% of the time, so per-trait counts are uneven (4–20 for `flat`, 1–19 for `non_rhyming`).
- **Why not all from the LLM:** the first pilots asked the LLM for all four types. Only about 1 in 10 of its `off_topic` and `flat` quatrains rhymed AABB, most `flat` and `non_rhyming` ones were in the third person ("She walks into the room…") while every diss says "you", and its `wrong_trait` roasts often failed the form check. The classifier could then learn "rhymes and says *you*" instead of trait fit. End-word tags without worked examples made it worse (the model tagged the first word of the line). Reusing the corpora gives `off_topic` and `wrong_trait` negatives that already pass, and the relabelled disses differ from the positives only in trait fit.
- Total: 2,235 negatives.

# Phase 2: Phonetic module [Core]

Build this first, since the data filters depend on it. Start from the helpers already in `quatrain_gen.ipynb` (`rhymes`, `identical_rhyme`, `line_syllables`, `oov_rate`), so the quatrain corpus and the diss data are checked with the same rhyme rules.

```python
import pronouncing
from g2p_en import G2p
g2p = G2p()

def phones(word):
    p = pronouncing.phones_for_word(word.lower())
    return p[0] if p else " ".join(g2p(word))   # fallback for unknown words

def rhyme_part(word):
    return pronouncing.rhyming_part(phones(word))

def rhymes(a, b):
    return a.lower() != b.lower() and rhyme_part(a) == rhyme_part(b)

def syllables(line):
    return sum(pronouncing.syllable_count(phones(w)) for w in line.split() if w.isalpha())
```

Then add:
1. **`aabb_score(lines)`**:
   - lines 1–2 and lines 3–4 each score 1 for an exact rhyme, 0.5 for a near rhyme (same final vowel), 0 otherwise
   - a small penalty if the A and B rhyme sounds are the same (which would make it AAAA)
   - average the two pairs
2. **`syllable_score(lines)`**: there's no fixed meter, so check two things:
   - each line falls within 7–11 syllables
   - the two lines in each rhyming pair are within 2 syllables of each other, so the couplets feel balanced
   - the corpus filter in 1a was looser (6–12 syllables, within 3), so some corpus quatrains will score below 1 here
   - **to check:** the disses follow the style CSV at 6–18 syllables within 5 (`diss_form`, median 13 per line), so a 7–11 target scores most real disses below 1. Consider aligning this range with `diss_form` before tuning the reranker weights.
3. **`lexical_score(line)`**: the fraction of words found in CMUdict or the GloVe vocabulary.
4. **Rhyme planner `plan_rhymes(traits)`** [Recommended]:
   - collect GloVe neighbours of the trait and its flip words
   - find rhyming pairs among them using CMUdict
   - pick **two pairs with different rhyme sounds**, one for lines 1–2 and one for lines 3–4
   - rank by similarity to the trait and return the top k plans, e.g. `[("proud","loud"), ("wise","eyes")]`
5. Unit tests with about 30 known rhyming and non-rhyming pairs.

# Phase 3: Generators

### Shared settings
- **Tokenizer:** BPE with `sentencepiece`, 8k vocabulary, trained on the quatrain corpus plus diss data. [Core]
- **Input format:**
  ```
  <traits> confident knowledgeable <intensity> harsh <rhymes> proud loud wise eyes <poem> ...line1 <nl> line2 <nl> line3 <nl> line4 <eos>
  ```
  During training, `<rhymes>` comes from the 1c annotation; at inference, from the rhyme planner. Use an explicit `<nl>` line-break token so the model learns where lines end. Loss is computed on poem tokens only.
- **Stage 1 pretraining** on the quatrain corpus (1a) uses empty `<traits>`, with `<rhymes>` taken from each quatrain's `rhymes` field. Every Stage 1 example is a real AABB quatrain, so the model learns the rhyme-conditioning format and the four-line shape before it sees any diss data.

### System A: GRU language model [Core]
- 300-dimensional embeddings, 2-layer GRU with 512 hidden units, dropout 0.3.
- Stage 1: train on the quatrain corpus until validation loss stops improving. It is about 20k quatrains (roughly 1M tokens), far smaller than Gutenberg, so expect more epochs and watch for overfitting. Stage 2: fine-tune on diss data at about 1/5 of the Stage 1 learning rate.
- AdamW, gradient clipping at 1.0, `ReduceLROnPlateau`, early stopping (patience 3), restore the best validation checkpoint.
- **Reversed lines.** Each line is written word-reversed, starting from its rhyme word, and that word is forced at decoding, so every line ends on the rhyme plan. With forward lines the GRU ended only 27% of lines on the planned word (6% full AABB); reversed it is 100%, with no loss in trait mentions or fluency. The forward run is kept as the ablation baseline (`gen_A_*`; final model `gen_A_rev_*`; results in `eval/results/gen_A/`).

### System B: GRU encoder-decoder with attention [Optional]
- The encoder reads traits, intensity and rhyme words; the decoder generates the poem with Bahdanau attention (Lab 5 code). Initialize the decoder from System A's Stage 1 weights where the shapes match.

### System C: small Transformer [Optional]
- Decoder-only: 4 layers, 4 heads, 256 dimensions. Same tokenizer, format and two stages as A (Lab 6 code).

### System D: Qwen2.5-1.5B-Instruct + LoRA [Recommended]
- **Why 1.5B:** clearly better English than 0.5B, still trains on a free Colab T4 and runs on a laptop GPU (RTX 3070, 8 GB) for the demo. Larger models are allowed by the brief but would make the generator do all the work and hide the planner and reranker contributions.
- `peft` LoRA with r=16, alpha=32, dropout 0.05 on the attention projections (q, k, v, o); 3 epochs on the diss data, lr 2e-4 with cosine schedule and 5% warmup, 16 examples per step (batch 8 × 2 accumulation), keeping the epoch with the best validation loss. No Stage 1: the base model already knows English.
- **Prompt:** a chat message with the same information as System A's prefix (traits, intensity, the four planned end words), so the comparison is fair.
- **End-word tags:** each answer line starts with its end word in brackets (`[late] you live by your clock, not a minute too late,`), the same trick as the quatrain generation (1a), so the model commits to the rhyme word before writing the line. The tags are stripped on decoding. Lines are written forward, so unlike System A nothing forces the end word; the reranker's `aabb_score` matters for D.
- **Repetition penalty** as in System A (1.2 on word tokens already in the answer), leaving out the prompt and the planned end words, which each appear twice. Qwen's own `repetition_penalty` is turned off, since it would also penalize the end words listed in the prompt.
- Code in `generation/qwen_lora.py`, driven by `generation/train_qwen.ipynb` (Colab T4, about 25–40 min; adapter saved to Drive as `gen_D_1.5b_best/`). The notebook ends with A and D on the same 80 prompts with the same checks (end-word hit, AABB, syllables, lexical, trait mention, distinct-2).
- **Size comparison** [Optional]: the checkpoint name follows `MODEL_NAME`, so 0.5B and 3B (`gen_D_0.5b`, `gen_D_3b`; batch 4 × 4 for 3B on a T4) run from the same notebook, to show how much the planner and reranker add as the generator grows.

### Decoding, for all systems
- Top-p 0.9, temperature 0.8, repetition penalty.
- **Batch** generation, e.g. `num_return_sequences=10` in a single call.
- Generate 10 candidates for each of the top 2 rhyme plans (about 20 total).
- **Stop after the fourth `<nl>`**, or at `<eos>`, so every candidate is exactly four lines. System D keeps the first four lines of its answer.

**Checkpoint, end of Week 10:** every system you're building produces readable quatrains for the 50 evaluation prompts.

# Phase 5: Reranker

1. **Trait-fit classifier** [Recommended]: fine-tune DistilBERT on `"[traits] [SEP] [poem]"`.
   - Positives: reviewed disses with their correct traits
   - Negatives: the 1e set (flat, non-rhyming, off-topic, and disses paired with a wrong trait), plus poems with shuffled lines
   - **Code:** `reranker/trait_fit.py` (splits, model, `TraitFit.score(traits, poems)` for the reranker), `python reranker/train_trait_fit.py`, or on a Colab T4 `reranker/train_trait_fit.ipynb` after uploading the zip from `python reranker/make_colab_zip.py` (sweep of lr 2e-5 and 5e-5 × seeds 42–44, chosen on val AUC; `trait_fit` in `config.yaml`). Saved as `checkpoints/trait_fit_best/`, results in `eval/results/trait_fit/`.
   - **Trait text:** each trait is written with its synonyms and flip side from `traits.json` (`confident: self-assured, bold, …, arrogant, all talk`), so held-out traits come with known words. The fallback disses have no traits and are left out.
   - **Splits** (built on the fly, fixed by the seed): `flat`, `non_rhyming` and `off_topic` are split 80/10/10 within each type. The 1e `wrong_trait` rows reuse train disses, so they stay in train, and val and test relabel their own disses the same way (never within a `CLOSE` group) at the train ratio. `shuffled` (20% of each split's disses) reorders the lines so neither couplet stays together. Test adds the 146 held-out disses, each also with a wrong training trait, plus as many training-trait disses labelled with a held-out trait. Result: train 5,808 / val 723 / test 1,189 rows (467 held-out), and no val or test poem appears in train.
   - Reported on test, training-trait and held-out-trait rows apart: AUC, accuracy/P/R/F1 at 0.5, how often each negative type is scored as a fit, and the time to score 5 candidates on GPU and CPU.
   - **Result** (`eval/results/trait_fit/`; Colab T4, about 21 s per epoch; chosen run lr 5e-5 seed 42, best epoch 4 of 5):

     | Test | n (pos) | AUC | Acc | P | R | F1 |
     |---|---|---|---|---|---|---|
     | training traits | 722 (402) | 0.984 | 0.971 | 0.961 | 0.988 | 0.974 |
     | held-out traits | 467 (146) | 0.966 | 0.927 | 0.850 | 0.932 | 0.889 |
     | all | 1,189 (548) | 0.984 | 0.954 | 0.930 | 0.973 | 0.951 |

     - Share of each negative type scored as a fit: `off_topic` and `non_rhyming` 0, `wrong_trait` 0.058, `flat` 0.079, `shuffled` 0.138. Shuffled lines are the weakest point; the phonetic `aabb_score` catches them in the combined score anyway.
     - The two learning rates tie on val (mean AUC 0.9762 for 2e-5, 0.9765 for 5e-5, seeds 42–44); on test they are within 0.003 AUC. Over all 6 runs: test AUC 0.970–0.984, held-out 0.928–0.966.
     - 0.009 s to score 5 candidates on the T4, 0.38 s on the Colab CPU.
2. **Combined score** [Core, with w5 Recommended]:
   ```
   score = w1·norm_logprob + w2·aabb_score + w3·syllable_score
         + w4·lexical_score + w5·trait_fit − w6·repetition − w7·toxicity
   ```
   Normalize log-probability by length, otherwise short poems win.
3. **Hard filters first:** drop any candidate that isn't 4 lines, has toxicity above the threshold, or has a lexical score below 0.8.
4. **Order for speed:** run the instant checks on all candidates, then run DistilBERT on the top 5 only.
5. **Weight tuning:** rate about 150 candidates on a 1–5 scale (at least two raters). Grid-search the weights to maximize Spearman correlation with those ratings.

# Phase 6: NLU [Recommended]

1. Joint intent and slot model: DistilBERT with an intent head on `[CLS]` and a BIO slot head on tokens (Lab 9 code), in `nlu/joint_model.py`. Each word's tag sits on its first word piece; the loss is intent plus tag cross-entropy. Batch 16, linear warmup over 10% of the steps, up to 10 epochs with early stopping (patience 2; `nlu` in `config.yaml`). Each run keeps the epoch with the best mean of val intent accuracy and per-word slot F1; per word, not exact span, because exact-span F1 jumps between epochs with the loose gold boundaries.
   - **Training:** `nlu/train_nlu.ipynb` on a Colab T4, after uploading the zip from `python nlu/make_colab_zip.py` (about 20 min). It runs a sweep, lr 3e-5 and 5e-5 × seeds 42, 43, 44, and every run is evaluated on test (`eval/results/nlu/sweep.json`). The learning rate with the best mean val score wins, then its seed with the best val score; test results are never used to choose. The chosen model is saved to the shared Drive as `checkpoints/nlu_joint_best/`.
2. **Slot normalization** (`nlu/normalize.py`): a trait key or another form of it (loyalty → loyal) or a synonym phrase from `traits.json` first; otherwise sentence embeddings (all-MiniLM-L6-v2): the span's 7 nearest labelled spans from the NLU train split vote, plus each trait's similarity to its description, with full weight for traits with no training spans (the held-out ones); below similarity 0.4 to everything it is unknown, and the nearest trait is kept for the dialogue manager.
   - **Why not GloVe:** most spans are indirect ("set financial goals for everything"). On the gold spans, the mean GloVe vector picked the labelled trait 20–33% of the time; the embedding kNN 39–57%. Many misses are a neighbouring trait (calm for easygoing), so the results are also given leniently, counting a trait from the same `CLOSE` group (`prepare_negatives.py`).
   - The 0.4 threshold keeps 94% of real val spans but rejects only 12% of non-trait phrases, so it is a safety net; deciding what is a trait is the tagger's job.
3. Report intent accuracy and slot F1 on the NLU test set, training-trait and held-out-trait messages apart, plus trait accuracy of the normalization (gold spans) and end to end (traits found in a message against its labels).
4. **Result** (`eval/results/nlu/`). Over the seeds, mean ± standard deviation:

   |---|---|---|---|---|
   | 3e-5 | 0.827 ± 0.003 | 0.934 ± 0.005 | 0.290 ± 0.008 / 0.649 ± 0.005 / 0.728 ± 0.004 | 0.295 ± 0.025 / 0.313 ± 0.018 |
   | 5e-5 | 0.828 ± 0.007 | 0.935 ± 0.003 | 0.310 ± 0.009 / 0.656 ± 0.009 / 0.733 ± 0.004 | 0.305 ± 0.024 / 0.321 ± 0.021 |

   The two learning rates are tied within the seed spread; 5e-5 won on mean val score. The chosen run (lr 5e-5, seed 44, epoch 8 of 10) on test:

   | Test | n | Intent acc | Slot F1 exact / per word / overlap | Traits found, exact / lenient |
   |---|---|---|---|---|
   | training traits | 332 | 0.910 | 0.300 / 0.662 / 0.718 | 0.280 / 0.396 |
   | held-out traits | 197 | 0.985 | 0.312 / 0.665 / 0.753 | 0.325 / 0.426 |
   | all | 529 | 0.938 | 0.306 / 0.664 / 0.736 | |

   - **The spread over seeds is under 0.01 on almost every metric, and per-word val F1 levels off around epochs 5–8**, so more training or tuning will not add much. The limits are the loose labels and the normalization.
   - **Slot F1 by exact span match is low because the gold boundaries are loose:** the LLM picked span lengths freely (gold "talk circles around", predicted "talk circles around your entire team"). The tagger usually finds the right words (overlap F1 0.74). In `NLU.parse`, predicted spans one word apart are joined, which raised trait accuracy end to end on val.
   - Normalization of the gold test spans: 0.44 strict / 0.58 lenient for training traits, 0.49 / 0.56 for held-out traits, the same in every run since it does not depend on the model. This is the weakest step.
   - Weakest intent: `make_meaner` (0.77, 30 test messages). Plain "make it meaner" can come out as `request_diss`, so the dialogue manager should check for meaner/softer keywords first.
   - 23 ms per message on the T4 and 66 ms on a laptop CPU, normalization included. On the CPU the model gives exactly the T4 test results.
5. **Spot check** (`spot_check.csv`, 348 messages, first pass by Claude, to be confirmed by the team): 42 (12%) marked wrong. About half are the wrong intent, mostly `greet` messages that are really `request_diss` and `another_one` messages that tell a new story; the rest are a neighbouring trait or a span that misses the trait words. These show up as model errors on the test set too.

# Phase 7: Dialogue manager [Recommended]

A rule-based state machine (Lab 10):

```python
state = {"traits": [], "intensity": "normal", "history": [], "awaiting": None}
```

| Situation | Action |
|---|---|
| `request_diss` with traits | update the state, generate, reply |
| `request_diss` without traits | ask for traits |
| `another_one` | regenerate with the same state, avoiding poems in `history` |
| `make_meaner` / `make_softer` | change the `<intensity>` token, regenerate |
| new traits mid-conversation | add them, or replace the old ones if the user says so |
| unknown trait | use the nearest trait and say so, or use a generic diss |
| `out_of_scope` | redirect back to the bot's purpose |

**Repeat avoidance:** penalize any candidate with ROUGE-L above 0.5 against a poem in `history`, and avoid reusing the same rhyme plan twice in a row.

# Risks and fallbacks

- **GRU output is incoherent by Week 10:** keep it as the baseline, make System D the main generator, and present the reranker and dialogue layer as the contribution.
- **Quatrain corpus is too small or too uniform for Stage 1:** raise `TARGET_USABLE` to 50,000, add topics or tones, or mix in output from a second model (e.g. Qwen2.5-32B) for more variety in style.
- **Diss data quality is weak:** cut to 25 traits and generate more per trait. Depth matters more than coverage.
- **The rhyme planner restricts vocabulary too much:** sample from its top 5 plans and include some unconstrained candidates.
- **Short on time:** drop Systems B and C and retrieval, use keyword-based NLU, and reduce the human evaluation to 20 prompts × 3 configurations, still with outside raters.

Weeks 8–9 decide the rest: the phonetic module and the data come first, because every other component depends on them.
